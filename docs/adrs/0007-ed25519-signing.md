# ADR-0007: Ed25519 over RSA for audit log signing

## Status

Accepted · 2026-06-06

## Context

Layer 5 produces cryptographically verifiable proof of every firewall decision for regulatory audits (EU AI Act Art. 12), GDPR subject access, and legal defense. Each audit entry must be signed and chained to detect tampering.

Signing algorithm choice affects signature size, verification speed, dependency footprint, and third-party auditability.

## Decision

**Ed25519** for per-entry signatures via **`@noble/ed25519`** (pure JavaScript, no native dependencies).

**SHA-256 hash chain:** each entry includes `previous_hash` — the SHA-256 of the prior entry's canonical serialization. Genesis entry uses `previous_hash` of 64 zero hex digits.

**Payload privacy in audit records:**
- `tool_call.arguments`: sanitized primitives only (PII fields omitted per policy).
- `tool_call.arguments_hash`: SHA-256 of full original payload — **required**.
- See [`schemas/audit-entry.schema.json`](../../schemas/audit-entry.schema.json).

Verification: workspace manifest includes Ed25519 public key; `aaf verify` validates chain + signatures independently.

## Practical application

```typescript
// Signing payload excludes signature field; includes arguments_hash
const payload = serializeForSigning(entry);
const signature = ed25519.sign(payload, privateKey);
```

- Local storage: SQLite append-only with triggers preventing UPDATE/DELETE.
- Cloud (Pro+): S3-compatible Object Lock / WORM.
- Enterprise: optional on-chain Merkle root anchoring (separate from per-entry algorithm).

## Consequences

### Positive

- 64-byte signatures — minimal storage overhead.
- Fast verification (~50 µs per entry).
- No native deps — cross-platform npm install without build tools.
- Modern standard with broad library support for auditors.

### Negative

- Some legacy enterprise tooling expects RSA-2048/4096.
- Ed25519 public keys less familiar to teams used to X.509 certificate chains.

### Mitigations

- Export manifest with public key in standard base64 format.
- Document verification procedure in [`audit-log.md`](../concepts/audit-log.md).
- Enterprise on-chain notarization adds external proof without changing entry format.

## Alternatives considered

### A. RSA-2048

Rejected. Larger signatures (256 bytes), slower verification, often requires native crypto modules or heavier deps.

### B. ECDSA secp256k1

Rejected. Ed25519 has simpler deterministic signing, better side-channel resistance story, and smaller keys.

### C. HMAC only (no asymmetric)

Rejected. HMAC requires shared secret — auditors cannot verify independently without the secret. Unsuitable for third-party regulatory audit.

### D. No signing, hash chain only

Rejected. Hash chain detects tampering but doesn't prove origin. Asymmetric signature required for non-repudiation.
